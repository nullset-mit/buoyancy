    /**

     * @param amount The transaction amount

        this(UUID.randomUUID(), date, memo, counterparty, amount, category);
    }

    /**
     * Constructs a new Transaction with the specified ID.
     *
     * @param id The UUID of the transaction
     * @param date The date of the transaction
     * @param memo The transaction description or memo
     * @param counterparty The counterparty involved in the transaction
     * @param amount The transaction amount
     * @param category The transaction category
     * @throws IllegalArgumentException if any parameter is invalid
     */
    public Transaction(UUID id, LocalDate date, String memo, Counterparty counterparty, 
                       BigDecimal amount, Category category) {
        if (id == null) {
            throw new IllegalArgumentException("Transaction ID cannot be null");
        }
        if (date == null) {
            throw new IllegalArgumentException("Transaction date cannot be null");
        }
        if (memo == null) {
            throw new IllegalArgumentException("Transaction memo cannot be null");
        }
        if (counterparty == null) {
            throw new IllegalArgumentException("Transaction counterparty cannot be null");
        }
        if (amount == null) {
            throw new IllegalArgumentException("Transaction amount cannot be null");

            throw new IllegalArgumentException("Transaction category cannot be null");

        if (amount.scale() > 2) {
            throw new IllegalArgumentException("Transaction amount cannot have more than 2 decimal places");

        this.id = id;
        this.date = date;
        this.memo = memo;
        this.counterparty = counterparty;
        // Ensure amount is stored with exactly 2 decimal places

        return amount.compareTo(BigDecimal.ZERO) > 0;

     * @return true if this transaction has a negative amount (debit), false otherwise

    public boolean isDebit() {
        return amount.compareTo(BigDecimal.ZERO) < 0;

### I'm now starting on the application package, and have a design question. Transactions come in to be classified by some means (csv, in this feature).
Until they are classified, my thought is that they should not be considered Transaction objects, and instead be a form of DTO. This class seems like it should live in the application layer (and package), as it will be needed there, and certainly can't be defined in an outer layer and used within the Application layer, as that would violate the central Dependency Inversion Principle. So, the questions are:
- Is a DTO for this sort of pattern wise (the pattern being outside input comes in to the application to be processed, after which it becomes a domain entity)
- If that is indeed the right solution, where should the DTO class (for a transaction line) live? My first though is the application package, and you will have to dissuade me to put it elsewhere.

Your analysis is spot-on, and I agree with your approach for several reasons:

1. **DTOs are appropriate here**: Using a DTO to represent the raw, unclassified transaction data from external sources (like CSV) is a wise design choice. This maintains a clear separation between external data formats and your domain model.

2. **Application package is the right location**: The application package is indeed the correct place for this DTO because:
   - It's part of the application's "port" that interfaces with the outside world
   - It respects the Dependency Inversion Principle by preventing domain entities from depending on input formats
   - The application layer is responsible for coordinating the translation between external data and domain objects

3. **Transformation responsibility**: The application layer would have the responsibility of transforming these DTOs into proper Transaction domain entities after categorization.

I would suggest something like `UnclassifiedTransactionDto` in the `net.mossworks.buoyancy.application.dto` package, which contains just the raw data needed before classification (date, memo, amount). Then your application service would handle the workflow of transforming these into proper domain entities.

This approach maintains clean architecture principles by keeping the concerns separated and dependencies flowing inward toward your domain.
